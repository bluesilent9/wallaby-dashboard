# Agent Build 25: queued local wallet renames (implementation contract)

Capability `wallet_rename_v1`. Dashboard owns operation lifetime and sends a full snapshot:
`{kind:"wallet_rename_queue",version:1,queue_id:64HEX,revision:NONNEGATIVE_INT,requests:[TASK]}`.

A TASK is exactly `{kind:"wallet_rename",version:1,nonce:64HEX,request_id:64HEX,rename_id:64HEX,chain,wallet:LOCAL_CORE_NAME_OR_DISC_ROUTE,new_name:DISPLAY_NAME,public_wallet,storage:"node"|"disc"}` plus `archive_id:64HEX` only for disc. `request_id` is the canonical SHA256 digest of all other fields. A `new_name` is 1–100 characters, at most 200 UTF-8 bytes, without paths/control characters; `.`/`..`/the reserved Extinct container are refused. Node watch-only names gain `_watch` unless already present. Persistent private-key wallets use the requested name. For multiple local multisig role wallets Dashboard must select unique per-role target names; one filesystem name cannot identify two different Core wallets.

The source `public_wallet` must be the exact public descriptor set of that local wallet/role. A shared public policy monitor must not be substituted for its distinct private cosigner account. For discs, use a currently loaded matching archive route and its encrypted-package archive ID; it remains queued until that archive is read/loaded locally. Names alone never identify a signer. Disc rename metadata preserves original signed wallet-creation proposals, account keys, policy codes and all old public policy revisions.

Signed outbox `wallet_rename_result` uses the existing setup-message envelope over `{version:1,queue_id,request_id,rename_id,status:"complete"|"archive_required"|"denied"|"error",wallet,new_wallet,storage,...evidence}`. Evidence: `identity_verified:true` for a verified node rename or locally approved disc metadata rename; `archive_skipped:true` only after the user explicitly chooses the locally permitted skip, otherwise archive completion includes full optical readback proof and image/old archive IDs. Receipt/queueing is not completion. `archive_required` acknowledges that a rename occurred and must block Dashboard cancellation just like complete; it still needs a verified replacement disc before that task is finished. Dashboard should cancel an operation only before any verified rename acknowledgement and withdraw its unattempted rows through a new full snapshot. Actual/uncertain attempts remain for reconciliation.

The Agent offers “Replacement archive is not required; this wallet will be made extinct” only when it independently finds a persistent private-key-enabled local wallet covering the **same complete signing account** as the loaded disc role. Another multisig cosigner is not a duplicate. Remote Dashboard assertions alone do not enable the option. This deliberately requires a locally verifiable duplicate; a remote-only duplicate is not enough.

Direct ordinary watch-wallet sync now derives a safe local destination from the sender's independently signed wallet name and appends `_watch`. Existing `Wallaby Extinct` grouped imports retain their reserved container name. Destination collisions are refused, never overwritten; history-recovery jobs record the final name before any mutation.

Dashboard Build 29 consumes this protocol. Private files and disc handling remain entirely on the locally approved Agent.

## Complete archive coverage and uncertain attempts

A node rename which has unloaded/moved a wallet but cannot verify reload sends `status:error,identity_verified:false,attempted:true,outcome_uncertain:true`. Dashboard must hold cancellation until locally reconciled; it cannot assume that an error means no rename took place. The Agent retains attempted task state and never replays the mutation.

Wallet-Builder-created discs must be included too, not just `archive_wallet` results. Build 25 emits a signed existing-kind `archive_inventory` after verified initial or replacement burning. It includes `event:"archive_verified"` (initial) or the existing `replacement_verified`, `archive_id`, `image_sha256`, `readback_verified:true`, `disc_count`, `replacements` and `members:[{member_id,policy_hash,name,role_id,public_wallet,related_policies}]`. This is public metadata only. Each physical role's public signing account is distinct from its shared multisig monitoring policy. Dashboard should persist these records, map them to each logical wallet by complete descriptors/account keys, and offer a rename task for every known old physical account. Earlier legacy discs with no stored encrypted-package ID need to be read/loaded once; routed getwalletinfo already exposes `wallaby_storage:"disc",wallaby_archive_id,wallaby_policy_hash`. Dashboard inventory should retain those fields and use the actual currently loaded signing route, never an original persistent wallet name, when routing an archive rename. Receipt of an archive_loaded route is not proof that a new replacement was burned.

The Agent does not modify the old signed setup proposal or its policy code to rename an archive. An authenticated `display_name` field is carried alongside the original recovery metadata. Its stable archive-member identity and every old public policy remain unchanged. Future disc restoration shows this display name and exposes new routing aliases while preserving the exact account keys.
